# Implementation prompt — Weekwise (Crit 7 MVP)

You are implementing **Weekwise**, a small full-stack ANU timetable planner for COMP4020 Crit 7.

The user wants a focused, polished prototype that demonstrates one real end-to-end flow with SQLite persistence. Keep the scope narrow. Do not turn this into a university-wide timetable platform.

## Outcome

Build a deployed-ready app where a student can:

1. select 3–4 preloaded ANU courses;
2. add one or more unavailable time blocks;
3. choose one main preference: fewer campus days, less time between classes, or fewer early classes;
4. generate valid timetable combinations;
5. compare up to three meaningfully different plans;
6. save one plan with a name;
7. reload the site and reopen the same saved plan from SQLite.

The app is a planning aid. It does not enrol the student, allocate classes, promise availability, or claim that every activity shown is available to every student.

## Scope decisions

Use these decisions unless repository evidence makes one impossible:

- One teaching period and one versioned timetable dataset.
- Three or four supported courses only.
- Course information is prepared once from an official **ANU Web Publisher Excel export**. Students do not manually enter every activity.
- The browser UI selects from preloaded courses. Do not build a general-purpose upload portal or scraper.
- Course catalogue data can live in a versioned normalized JSON file generated by an import script. SQLite is required for saved user plans and their conditions/selections.
- Use an anonymous browser session cookie to keep each visitor's saved plans separate. No account or ANU login.
- Use a deterministic TypeScript solver. Do not use an LLM for scheduling or explanations.
- Show at most three different representative plans. If only one or two distinct plans exist, show only those.
- Use a desktop weekly grid and a readable day-by-day list on narrow screens.

Do not add sharing, calendar export, live enrolment, capacity tracking, maps, walking-time estimation, notifications, social comparison, admin dashboards or automatic timetable scraping.

The normalized data model must express:

```ts
type Course = {
  id: string;
  code: string;
  title: string;
  activityGroups: ActivityGroup[];
};

type ActivityGroup = {
  id: string;
  label: string;       // e.g. Lecture A, Tutorial A, Lab A
  options: ActivityOption[];
};

type ActivityOption = {
  id: string;
  label: string;
  meetings: Meeting[]; // one option may require several meetings
  eligibilityNote?: string;
};

type Meeting = {
  weekday: 1 | 2 | 3 | 4 | 5 | 6 | 7;
  startMinute: number;
  endMinute: number;
  weeks?: number[];    // omit only when the source truly applies every supported week
  location?: string;
  mode: "in-person" | "online";
};
```

Selecting a course means selecting exactly one option from every required activity group. An option with several meetings is selected as a whole.

Add a visible data notice containing the teaching period, source, import/review date and this warning:

> Planning data only. Confirm class availability and allocation in ANU MyTimetable.

## Core planner behaviour

### Hard conditions

The user may add unavailable blocks with:

- label;
- weekday;
- start time;
- end time.

A candidate timetable is valid only when:

- it contains one option from every activity group of every selected course;
- no meetings overlap when their teaching weeks overlap;
- no meeting overlaps an unavailable block;
- any activity option explicitly locked by the user is present.

Use half-open intervals: `[start, end)`. Therefore 10:00–11:00 and 11:00–12:00 do not overlap.

If week information is present, meetings at the same weekday/time in disjoint teaching weeks do not conflict.

### Preference and ranking

Expose exactly three primary preferences:

1. **Fewer campus days** — number of weekdays containing at least one in-person meeting;
2. **Less waiting** — sum of gaps between consecutive synchronous meetings on the same day;
3. **Fewer early classes** — number of meetings starting before 10:00.

Use deterministic lexicographic ordering:

- campus-days mode: campus days → gaps → early classes → stable option IDs;
- gaps mode: gaps → campus days → early classes → stable option IDs;
- early mode: early classes → campus days → gaps → stable option IDs.

Do not invent a hidden score or percentage.

### Representative plans

Always include the first plan under the selected preference. Then consider the best plans under the other two preferences. Remove duplicate option combinations and avoid displaying several cards with identical metrics unless their class choices are meaningfully different and the difference is shown.

Each plan card shows:

- campus days;
- weekly gap minutes;
- early-class count;
- one short factual trade-off compared with the selected best plan.

When the user changes a condition, regenerate results and prevent an older asynchronous response from overwriting the latest state.

### No-solution state

Give a concrete explanation when possible, such as a locked tutorial overlapping an unavailable block. Preserve the user's conditions.

For the MVP, test each hard condition individually by removing it and rerunning the solver. Suggest a relaxation only when it actually restores at least one valid plan. The user must click the suggestion before the condition changes.

If the solver has not completed its search, do not report “no valid timetable”.

## Pages and interface

Keep the information architecture small:

- `/` — planner and result comparison;
- `/plans/` — saved plans for the current anonymous browser session;
- `/plans/[id]/` — reopen and edit a saved plan;
- `/about-data/` — source, coverage and limitations;
- `/readme/` — existing README contract.

On the planner page:

- course selection comes first;
- “Must satisfy” contains unavailable blocks and locked activities;
- “What matters most?” contains the three preference choices;
- results show the plan cards, the selected timetable and a save form;
- one primary heading is used;
- colour is paired with course codes and activity labels;
- all controls work with a keyboard;
- mobile layout uses a day-by-day agenda instead of a compressed timetable grid.

Use calm, restrained styling suitable for an ANU student tool. Keep the timetable visually dominant. Avoid dashboard filler and decorative statistics.

## Persistence

Use SQLite through the repository's existing Drizzle setup.

Keep the database schema small. A reasonable design is:

- `sessions`: anonymous session ID/token hash and timestamps;
- `plans`: plan ID, owner session, name, dataset version, preference, revision, timestamps;
- `plan_courses`: selected course IDs;
- `plan_selections`: selected option for each activity group and whether it is locked;
- `unavailable_blocks`: label, weekday, start and end minute.

Adjust this only when the existing starter offers a simpler established pattern.

The save endpoint must:

1. identify the anonymous session from a secure cookie;
2. load course data on the server;
3. validate all referenced course/group/option IDs;
4. rerun conflict checks and metric calculation;
5. write the complete plan in one transaction;
6. return success only after commit.

All read, update and delete queries must include the owner session. Use a revision value or equivalent check so two open tabs cannot silently overwrite one another.

The user-visible persistence demonstration is:

1. create a named plan;
2. reload the page;
3. open it from `/plans/`;
4. see the same courses, unavailable blocks, option selections and preference.

## Deployment

The final app must run at its Fly.io URL and keep SQLite data across a restart and redeploy.

Use the starter's Fly volume pattern. Ensure the production database file is stored on the mounted volume rather than inside the disposable application image. Do not place a volume-dependent SQLite migration only in Fly's default `release_command`, because that temporary machine does not receive the persistent volume. Follow or repair the starter's volume-aware migration approach.

Before declaring deployment complete, save a plan online, reload it, restart the app or machine in a controlled way, and verify the plan still exists.

## Meaningful tests

Keep the test suite focused. Add tests for these contracts:

1. adjacent meetings are allowed, overlapping meetings are rejected;
2. meetings in disjoint teaching weeks do not conflict;
3. every required activity group contributes exactly one option;
4. an option containing multiple meetings is rejected if any meeting conflicts;
5. changing the main preference changes ordering without changing the valid set;
6. removing a suggested hard condition really restores a valid result;
7. a saved plan survives reload and is isolated from another anonymous session;
8. the existing `pnpm check` suite and route invariants still pass.

Use a small hand-checkable fixture for solver tests. Do not write tests that merely mirror CSS or component implementation.
